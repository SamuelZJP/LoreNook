# LoreNook 归档流程

[English](../../backend/12-archiving-workflow.md) | [中文文档索引](../index.md)

更新日期：2026-10-19

## 1. 职责与实现

确认归档时，先保存用户认可的回合正文，再依次执行状态更新、回合摘要、情节判定及必要的情节摘要。任何一步失败即停止，已提交的正文与结果保留；重试从当前步骤继续。

| 文件 | 职责 |
| --- | --- |
| `schemas/archive.py` | 确认、重试、回合读取与进度契约 |
| `workflows/archive.py` | 确认保存、顺序编排与恢复 |
| `api/archive.py` | 确认、重试及回合查询入口 |
| `repository/archive.py` | 各步结果与步骤的原子保存 |

复用四个已有步骤 Workflow 及原有表，无新增迁移或依赖。模型请求不持有数据库会话，确认归档不执行写作预设。

## 2. 确认入口

`POST /api/chats/{chat_id}/archive` 接收写作结果中以下三个字段：

```json
{
  "user_input": "用户确认的输入",
  "ai_output": "<content>用户认可的正文</content>",
  "based_on_round_id": null
}
```

`based_on_round_id` 必须显式提供，首回合为 `null`，其后为生成候选时最新的已归档回合 ID。沿用写作结果中的同名字段。用户输入允许空字符串，完整 AI 输出必须包含唯一、闭合、非空的 `<content>` 正文；输入、标签、其他区段及换行均原样保存。

确认流程：

1. 校验正文标签。
2. 在短写事务中确认聊天存在、当前最新回合与 `based_on_round_id` 一致，且已完成归档。
3. 确认聊天角色、身份及初始或上一状态存在；保存下一序号的正式回合，步骤为 `state_update`。
4. 提交正文事务，随后依次执行剩余步骤。
5. 全部完成时返回 201 及最终进度。

客户端提交的是已经认可的候选，服务器不保存待确认候选，也不使用当前预设重新解析旧候选。`based_on_round_id` 检查回合顺序，不作为全部资料内容的版本号。后续状态更新使用执行时读取的资料及上一状态。

同一个确认请求重复提交时，旧的 `based_on_round_id` 不再匹配，返回 409；即使第一次已经完成，也不会再创建一条相同回合。并发确认在写事务内串行检查。客户端若未收到首次响应，应先查询最新归档进度；继续已有回合使用重试入口。

## 3. 步骤与事务

```text
保存正文 → 状态更新 → 回合摘要 → 情节判定 → 情节摘要 → 完成
                                      └─ 无需情节 ───→ 完成
```

每个步骤调用原有独立 Workflow，使用相同的状态校验器和近期摘要设置。状态更新与回合摘要各调用一次模型；情节判定不调用模型；需要情节时再调用一次情节摘要模型。

正文和每步结果分别提交。已成功的状态、摘要和判定范围不会因后续失败而撤销。情节摘要继续使用已保存范围，不重新判定，也不提前移动覆盖边界。

编排只根据本次步骤成功返回的下一步骤继续，不读取并接管另一个请求已经推进到的步骤。各步骤仍执行生成前检查和保存时的输入核对；并发请求可能同时调用当前模型步骤，但只允许一份结果成功保存，后到请求返回冲突，不覆盖先到结果或继续执行后续步骤。

未完成归档时，既不能写作，也不能确认下一回合。完成后可开始下一回合，或使用已有状态、摘要、情节编辑入口修改最新回合结果；不能重新执行完整归档。

## 4. 失败、恢复与错误

正式回合保存前的校验或事务失败不产生新回合。保存后的模型、解析、校验和判定错误由对应步骤记录 `archive_error`，停留在当前步骤。

配置缺失、输入变化、步骤冲突等前置检查错误不会覆盖归档错误。确认正文已经保存时，响应仍提供当前进度；修复配置后可继续。数据库或进程异常导致请求未正常返回时，客户端查询持久化进度恢复，不依据客户端记忆猜测当前步骤。

`POST /api/chats/{chat_id}/rounds/{round_id}/archive/retry` 接收：

```json
{"expected_step": "round_summary"}
```

只接受四种未完成步骤，不接受替代正文、状态或范围。目标必须是本聊天最新未完成回合，当前步骤必须与 `expected_step` 完全一致。成功重试当前步骤后自动继续后续流程，返回 200。

允许恢复尚未留下错误记录的步骤，例如正文保存后进程中断，或某一步成功提交后下一步尚未启动。无需人为制造失败标记。不自动重试模型或执行后台任务；每次恢复由客户端显式发起。

可识别的步骤业务或模型错误保留原有 HTTP 状态码与 `detail`，并附加 `archive` 进度对象。正文保存前的错误不附加该字段。

| 状态 | 含义 |
| --- | --- |
| 404 | 聊天或目标回合不存在、归属不符 |
| 409 | 旧候选、前一归档未完成、非最新目标、步骤已变化、配置或资料缺失、并发冲突 |
| 422 | 请求字段、正文、状态校验、模型配置或生成内容无效，或情节判定失败 |
| 502 / 504 | 模型调用失败 / 超时 |

错误沿用已有脱敏处理，不附加上游响应正文或模型鉴权。正式回合与生成结果仍按原文返回。

## 5. 查询契约

| 接口 | 返回 |
| --- | --- |
| `GET /api/chats/{chat_id}/archive` | 最新回合的归档进度；尚无正式回合时为 `null` |
| `GET /api/chats/{chat_id}/rounds` | 按序返回所有正式回合，包含归档未完成回合 |
| `GET /api/chats/{chat_id}/rounds/{round_id}` | 指定回合的归档进度，可读取历史回合 |

进度对象含三个字段：

- `round`：ID、聊天 ID、序号、用户输入、完整 AI 输出、摘要、当前步骤、错误、情节判定与范围、创建时间。
- `state`：本回合已保存的状态，尚未产生时为 `null`，不回退到初始或其他回合状态。
- `episode`：本回合产生的情节，尚未产生或无需情节时为 `null`；不返回覆盖本回合的其他情节。

列表和查询均检查聊天归属。读取已有进度不要求当前模型、预设或角色 Schema 可执行，不调用模型、不修改记录。

## 6. 验证

依赖检查通过。覆盖写作候选确认、原文保存、无情节与需情节的完整流程、四步失败与恢复、修复模型绑定/接口/Schema 后继续、已提交结果保留、情节范围保留、每步进程中断恢复、事务回滚、并发确认和并发重试、旧候选与越界拒绝、步骤校验、查询及待完成期间阻断写作。

完整无情节归档调用两次模型，需要情节时调用三次；重试不会重跑已经成功的模型步骤。网络测试全部使用模拟传输。
