# LoreNook 后端总览

[English](../../backend/README.md) | [中文文档索引](../index.md)

更新日期：2026-10-19

后端负责聊天数据、写作生成、记忆装配与顺序归档。业务规则见[产品设计](../design/product-design.md)，字段与归属见[数据模型](../design/data-model.md)。本文说明技术选型、模块划分和协作方式。

## 1. 技术选型

| 项目 | 选型 | 用途 |
| --- | --- | --- |
| 后端语言 | Python | 文本处理、模型调用与流程编排 |
| API 框架 | FastAPI + Pydantic 2 | 请求入口、数据校验与接口文档 |
| 数据库 | SQLite | 个人使用场景下的轻量持久化 |
| 数据访问 | SQLAlchemy 2 + Alembic | 数据模型、事务与数据库结构变更 |
| 模型调用 | HTTPX + 按接口类型划分的适配器 | 发送完整请求体，保留接口响应结构 |
| 验证 | pytest | 模块验证与写作、归档流程验证 |

### 1.1 定义模板

使用 Jinja2，在定义原文中编写变量、条件和循环。每次发送传入最新状态的完整 JSON 副本，由模板按需引用字段，例如 `state["世界"]["时间"]`。

执行环境采用 `ImmutableSandboxedEnvironment` 和 `StrictUndefined`。缺失变量或解析错误直接使发送失败；无模板的定义保留原文，不经过模板引擎。解析结果仅用于本次请求。

### 1.2 写作预设

使用 JavaScript 源码，保存在 `writing_presets.source` 中，由后端通过 QuickJS 执行。每份预设约定两个入口：

| 入口 | 输入 | 输出 |
| --- | --- | --- |
| `build(materials)` | 已解析定义、历史、First Message、当前输入和最新状态等材料 | 目标接口类型与完整请求体 |
| `parse(response)` | 模型接口的 JSON 响应 | 校验通过的完整 AI 输出文本 |

执行环境只提供输入数据和必要的纯函数，不提供网络、文件和数据库接口，并设置执行时间与内存上限。调用前后分别执行，数据通过 JSON 交换，不依赖跨调用的运行时状态。模型调用由 LLM 层执行。

当前通过 `quickjs-ng` 接入 QuickJS，已实现预设管理、独立执行与聊天请求预览。`build` 返回 `{api_type, body}`，`parse` 返回完整 AI 输出字符串；材料与执行约定见[写作预设模块](05-writing-presets.md)。

定义模板负责文本中的动态片段，写作预设负责请求对象构造、消息合并、返回提取与校验，两者独立执行。

模型调用已接入 HTTPX 与 `google_generate_content` 适配器，支持配置管理、按用途读取配置、递归补齐默认参数及单次调用。调用期间不持有数据库事务；接口和错误约定见[模型调用模块](06-model-calls.md)。

### 1.3 状态与事务

数据库采用短事务：创建聊天及复制数据在一个事务中完成；归档每一步的结果与步骤推进在同一个事务中保存。模型调用期间不持有数据库事务。

后端主要业务模块已实现并具有对应验证。角色状态 Schema 使用保存在角色记录中的 Python/Pydantic 源码，默认值生成、校验修正与状态更新约定见[状态模块](08-state-updates.md)。

## 2. 分层与目录

以下为后端代码的主要目录；完整分工见[项目结构](../architecture/project-layout.md)：

```text
backend/
├─ main.py          # 应用入口
├─ config.py        # 运行配置
├─ api/             # 请求入口
├─ schemas/         # 接口及模块间的数据结构
├─ workflows/       # 跨模块流程编排
├─ modules/         # 业务模块
├─ llm/             # 模型调用与接口适配
├─ repository/      # 数据模型与数据库读写
├─ shared/          # 正文提取、公共错误类型
├─ migrations/      # 数据库结构变更
└─ tests/           # 测试
```

| 层 | 职责 |
| --- | --- |
| `api` | 接收请求、校验参数，调用业务模块或流程，返回结果 |
| `workflows` | 组织跨模块调用，控制步骤顺序、保存时机和失败重试 |
| `modules` | 实现各项业务规则，提供查询、编辑、解析或生成能力 |
| `repository` | 定义存储模型，执行数据库查询和写入 |
| `llm`、`shared` | 提供模型调用及公共处理能力 |

调用关系：

```text
API → 业务模块                         # 查询与编辑
API → Workflow → 多个业务模块          # 创建聊天、写作、归档
业务模块 / Workflow → Repository       # 数据读写
Workflow / 生成模块 → LLM              # 模型调用
```

API 负责入口，Workflow 决定流程，模块负责具体处理。数据库操作集中在 Repository，模型请求集中在 LLM。

## 3. 业务模块

| 模块 | 目录 | 职责 |
| --- | --- | --- |
| 角色 | `modules/characters` | 角色资料、First Message、角色状态配置的管理 |
| 用户身份 | `modules/users` | 角色扮演身份的管理 |
| 聊天 | `modules/chats` | 聊天查询、配置及最新回合结果的编辑 |
| 定义 | `modules/definitions` | 定义编辑、排序、启用和模板解析 |
| 记忆装配 | `modules/memory` | 按 X、Y 和情节范围选择历史表示 |
| 写作预设 | `modules/presets` | 管理预设，执行请求包装与返回解析 |
| 模型配置 | `modules/models` | 来源库、聊天内配置与模型用途绑定 |
| 状态 | `modules/state` | 初始状态、状态读取与编辑、增量更新及 Schema 校验 |
| 回合摘要 | `modules/round_summary` | 根据本回合内容及更新后的状态生成摘要 |
| 情节判定 | `modules/episode_decision` | 选择判定方法，返回无需生成或截止回合 |
| 情节摘要 | `modules/episode_summary` | 为选定的连续回合范围生成情节摘要 |
| 数据管理 | `modules/admin` | 全量读取、按版本原子批改及最终一致性校验 |

各生成模块保存自己的提示词和处理逻辑。情节判定通过 `dispatcher` 选择 `methods` 下的方法，第一版只实现跨日与回合数阈值判定。

## 4. 聊天创建

`workflows/create_chat` 负责：

1. 创建聊天记录。
2. 复制角色、用户身份、定义、写作预设和模型配置，生成新的 ID 并重建关联。
3. 根据角色 Schema 默认值生成初始状态快照。
4. 保存聊天内的预设选择与模型用途关联。

First Message 随角色复制，作为第 0 楼。创建完成后，每个聊天使用自己的数据副本。

## 5. 写作流程

`workflows/writing` 负责一次发送或归档前的重新生成：

```text
读取聊天数据与最新状态
  → 解析已启用的定义
  → 装配历史情节、回合摘要和最近完整回合
  → 加入 First Message、当前输入和最新状态
  → 写作预设包装请求
  → LLM 执行一次调用
  → 写作预设解析、校验返回
  → 返回待确认的 AI 输出
```

预设使用经过必要解析的数据库原文。历史选取由记忆装配模块完成，材料在请求体中的组织方式由预设决定。First Message 始终提供给预设，由预设决定是否包含。

LLM 层检查目标接口兼容性，处理连接、鉴权与请求参数；预设参数优先，模型配置补充默认值。预设仅执行调用前后的内容转换。

定义解析或写作处理失败时，本次发送失败。生成成功的回复等待用户确认，点击归档时才保存正式回合。

当前已实现 `POST /api/chats/{id}/writing`，发送与归档前重新生成使用同一入口。材料及模型配置在同一读事务中取得，事务外完成包装、调用与解析，返回结果不落盘。接口、快照与错误约定见[写作流程模块](07-writing-workflow.md)。

## 6. 归档流程

`workflows/archive` 保存已确认的用户输入与完整 AI 输出，随后依次执行：

```text
更新状态 → 生成回合摘要 → 判定情节 → 生成情节摘要 → 完成
                            └─ 无需情节 ─────────→ 完成
```

| 步骤 | 保存结果 |
| --- | --- |
| 状态更新 | 本回合完整 JSON 状态快照 |
| 回合摘要 | 本回合摘要 |
| 情节判定 | 是否需要情节，以及选定的起止回合 |
| 情节摘要 | 摘要、覆盖范围及产生该情节的回合 |

归档模块读取 AI 输出时只使用 `<content>` 正文，用户输入另行提供。状态更新使用修改指令生成新快照，再由 Schema 校验与修正；回合摘要使用更新后的状态。

第一版情节判定在排除最新回合后，候选至少有 5 个且最新两回合的 `世界.日期` 不同时，归纳最新回合之前的全部候选。判定使用状态与回合数，不调用模型、不设置兜底。情节保存成功后才形成新的已归纳范围。

每一步结果保存成功后推进 `archive_step`。失败时记录 `archive_error` 并停在当前步骤，用户仅能重试该步骤，成功后继续。情节摘要重试使用已保存的判定范围。

当前已接入[状态更新](08-state-updates.md)、[回合摘要](09-round-summaries.md)、[情节判定](10-episode-decisions.md)和[情节摘要](11-episode-summaries.md)的独立步骤入口，并由[归档流程](12-archiving-workflow.md)串联确认保存、自动执行和失败恢复。回合摘要使用本回合已保存状态；判定不调用模型；情节摘要按序归纳选定范围的摘要、用户输入、AI正文和对应状态，结合首条消息或只读桥接信息，生成并分别保存标题与摘要，保存成功后完成归档。

归档完成后才能发送下一回合。成功的归档仅允许编辑最新回合的摘要、状态和本次情节，修改立即保存，不触发重新生成。[数据管理模块](13-data-management.md)提供独立的全量读取与批量修改入口，允许修改历史数据，按原文保存状态并检查最终关联与归档一致性。
