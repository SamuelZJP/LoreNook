# LoreNook 数据管理模块

[English](../../backend/13-data-management.md) | [中文文档索引](../index.md)

更新日期：2026-10-19

## 1. 职责与实现

提供业务数据库的全量读取和原子批量增删改，允许修改历史回合及其状态、摘要、情节、归档步骤、主键、归属和创建时间，不受聊天面板仅编辑最新归档结果的限制。提交后立即生效，不自动重新生成其他结果。

| 文件 | 职责 |
| --- | --- |
| `schemas/admin.py` | 十张业务表的字段契约、操作和读写结果 |
| `repository/admin.py` | 固定表注册、参数化读取与修改、外键检查 |
| `modules/admin/service.py` | 数据快照、读取版本及批量处理 |
| `modules/admin/consistency.py` | 最终记录之间的一致性校验 |
| `api/admin.py` | 数据管理 HTTP 入口 |

使用现有物理结构，无新增迁移或依赖。Alembic 版本表与 SQLite 内部表不属于业务数据，不开放修改；接口不执行客户端 SQL。

## 2. 全量读取

| 接口 | 返回 |
| --- | --- |
| `GET /api/admin/schema` | 各表名称、主键字段及完整行的 JSON Schema |
| `GET /api/admin/data` | `revision` 和 `tables` 全量数据快照 |
| `GET /api/admin/data?include_secrets=true` | 同样的完整快照，包含模型 `api_key` 原文 |

包含 `chats`、`characters`、`user_identities`、`definitions`、`writing_presets`、`model_configs`、`chat_model_bindings`、`rounds`、`state_snapshots` 和 `episodes`。每表按主键稳定排序；读取不执行 Schema、模板、预设或模型。

默认模型记录省略 `api_key`，返回 `has_api_key`。显式读取密钥时返回 `api_key`，不附加该派生字段。两种读取使用相同的数据库版本。修改模型配置时省略 `api_key` 保留原密钥，传入空字符串清空；`has_api_key` 不可写。

时间使用带时区的 ISO 字符串，存储后统一读取为 UTC。源码、正文、空白、换行及 JSON 值类型保留。

## 3. 批量修改契约

`POST /api/admin/data` 接收最近读取的 `revision` 作为 `expected_revision`，以及至少一条操作：

```json
{
  "expected_revision": "最近读取的版本",
  "operations": [
    {
      "action": "update",
      "table": "rounds",
      "key": {"id": "目标回合ID"},
      "values": {"summary": "修改后的历史摘要"}
    }
  ]
}
```

| 操作 | 字段与行为 |
| --- | --- |
| `create` | `table`、`values`；创建一行，可显式给出 ID 和时间，省略时生成默认值 |
| `update` | `table`、`key`、`values`；只覆盖提供的字段，省略字段保持原值，允许修改主键 |
| `delete` | `table`、`key`；删除指定行，并执行数据库级联删除 |

`key` 必须完整且仅包含主键。一般为 `{"id":"记录ID"}`，用途绑定为 `{"chat_id":"聊天ID","purpose":"writing"}`。修改主键后，后续操作使用新主键。

成功返回 200：

```json
{
  "revision": "提交后的版本",
  "changes": [
    {"action": "update", "table": "rounds", "key": {"id": "目标回合ID"}}
  ]
}
```

`changes` 按操作顺序返回显式目标，新增或改名记录返回最终主键，不返回密钥或全量行。级联删除结果通过重新读取快照确认。

## 4. 事务与版本检查

整批操作在一个 `BEGIN IMMEDIATE` 短事务内完成。首先检查整个业务数据库的内容版本，任何来源的数据修改，包括归档结果和密钥变化，都会使旧版本失效。版本由按固定规则序列化后的全量字段内容计算，不新增持久化版本列。内容完全相同的操作不改变版本。

操作按请求顺序执行。外键允许在同一批中暂时悬空，提交前统一检查，便于重建关联和修改 ID；唯一性、非空和单行检查仍逐条生效。例如交换回合序号时，应先使用未占用的正整数作为临时值，再完成交换。

执行所有操作和级联动作后，重新读取最终数据，校验字段、外键及业务一致性。任一操作不存在、字段无效、引用不合法、版本冲突或校验失败，整批回滚。不会部分保存有效操作；数据库级联之外的关联修复由请求明确给出。

两个客户端持有相同版本并发提交不同修改时，只有先取得写锁并提交的修改成功，另一个返回 409；客户端重新读取后再决定如何提交。

## 5. 校验规则

数据管理中的状态按原文保存，检查有限数值的 JSON 对象、统一世界字段及记录关联，不执行角色 Schema 或自动修正。统一约束见[状态模块](08-state-updates.md)。仅本次创建或更新的状态行需满足新约定；读取及未修改的旧状态不强制迁移。源码可作为未完成草稿保存，AI 输出也可直接修改为任意原文。聊天面板状态编辑和正常状态更新继续执行各自的 Schema 与正文校验。

字段按严格类型校验：数字不接受字符串或布尔值，非空字段不接受 `null`，ID 非空且不超过 36 字符，时间必须带时区。JSON 不接受 NaN、Infinity 或不可编码文本。未知表、字段或操作返回错误。

最终数据库必须满足：

- 聊天保留角色、身份及角色初始状态；来源资料仍可独立存在。
- 聊天内回合从 1 连续编号，仅最新回合可以尚未归档完成。
- `state_update` 无本回合状态、摘要和判定；`round_summary` 有状态、无摘要和判定；`episode_decision` 有状态和摘要、尚无判定。
- `episode_summary` 有状态、摘要和需要情节的已保存范围，尚无本次情节；`complete` 的状态、摘要、判定及必要情节均齐全。
- 情节端点和产生回合属于同一聊天，范围正向、连续、覆盖已归档回合，并截止于产生回合之前。
- 已保存情节与产生回合的判定范围完全一致；按产生回合顺序，每个情节从最早未归纳回合开始，不重复覆盖或跳过历史。
- 待生成情节同样从当前最早未归纳回合开始，不提前改变覆盖边界。
- 预设选择、模型用途、定义归属及状态归属继续满足数据库外键、唯一性和字段约束。

例如缩短已保存情节的范围时，必须同批修改情节及产生回合的判定端点。删除历史回合时，需要同批处理引用它的情节、判定范围和后续序号。删除整个聊天会正常级联清理其副本与历史，来源库保留。

修改历史正文、状态或摘要不会重算后续状态、摘要或情节，也不重新执行跨日判定。数据管理只检查结果组合一致，不要求人工修改的判定重现当前内置方法的计算结果。

## 6. 错误与验证

- 404：目标记录不存在。
- 409：读取版本已变化，或数据库约束、最终关联和归档一致性不满足。
- 422：操作、主键形状、字段类型、JSON 或时间格式不合法。

错误不包含提交的字段值、模型密钥或 SQL 参数。错误后原快照及其版本保持不变。

依赖检查通过。覆盖十表完整创建、前向引用、默认值与创建时间、历史原文修改、Schema 不执行、主键与归属重建、范围联合修改、删除级联、历史删改与重编号、归档结果匹配、多段情节与待生成范围、跨聊天引用、严格 JSON 类型、密钥读取与更新、版本冲突、并发写入及事务回滚。
