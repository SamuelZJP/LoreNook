## 1. 项目目标与范围

LoreNook 是面向个人使用的轻量 AI 角色扮演工具，围绕聊天、记忆和写作预设构建。

核心体验是按回合推进故事：生成回复后由用户确认，再正式保存回合并更新记忆。当前回合归档成功后，才允许发送下一回合。

第一版范围：

- 聊天生成、重新生成、确认归档。
- 回合摘要、状态更新、情节判定与情节摘要。
- 基于情节、回合摘要、最近完整回合的分层记忆。
- 写作请求的预设包装与回复解析。
- 定义编辑、预设编辑、数据修改和设置界面。

当前不实现生图和语音，但界面与内容模型应考虑未来增加这些内容。暂不考虑待确认回合的临时保存与恢复。第一版写作预设只支持一次模型调用的前后转换。

## 2. 界面框架

| 页面 | 主要职责 |
| --- | --- |
| 角色扮演 | 展示聊天楼层、摘要、情节和最新状态；提供生成与归档操作 |
| 定义编辑 | 编辑角色、用户身份及其他定义 |
| 预设编辑 | 编辑写作请求包装与回复解析规则 |
| 数据修改 | 全量修改数据库，允许修改任何部分，不受聊天面板仅操作最新回合的限制 |
| 设置 | 摘要相关设置、模型设置、样式设置、前端解析设置及其他设置 |

聊天界面只展示最新状态，也可展示摘要和情节。聊天面板中的生成、重试和编辑操作只针对最新回合及其归档结果。

前端解析设置负责 AI 输出各区段的显示、隐藏、折叠和渲染。预设中的自定义 `think` 标签不是模型接口的原生思维链，两者应区分。

## 3. 核心概念

| 概念 | 定义 |
| --- | --- |
| 聊天（Chat） | 以某个用户身份与某个角色进行的完整聊天，直接或间接关联回合、记忆、状态等内容 |
| 角色 | 包含姓名、头像、元数据描述等信息的角色对象 |
| 用户身份 | 用户在角色扮演中采用的身份，包含姓名、头像、元数据描述等；不等同于多用户账号体系 |
| 定义 | 分为角色定义和用户定义，分别归属于角色和用户身份；是类似广义世界书的设定条目 |
| 定义模板解析 | 在定义进入请求包装前，根据当前最新变量将定义中的模板内容解析成本次请求使用的文本 |
| First Message | 归属于角色的一段独立开场数据，在聊天面板显示为第 0 楼，并提供给写作预设 |
| 回合 | 一次用户输入与一次被用户认可的 AI 输出 |
| 回合摘要 | 对一个回合发生内容的概括 |
| 状态 | 某个回合结束时的状态，以 JSON 表达和存储，包含时间、地点、人物信息及其他状态变量；最新状态是定义模板解析的变量来源 |
| 情节 | 对连续若干回合的摘要，记录明确的起止回合 |
| 写作预设 | 将结构化写作材料包装为目标接口请求，并将模型返回校验、拆解为可接受 AI 输出的转换规则 |

已成功归档的回合必须具有摘要和状态；待确认或归档未完成的回合可以尚未具备这些结果。

创建聊天时，复制所选角色、用户身份及其定义、First Message、状态配置等数据，形成该聊天的独立快照。不同聊天的角色、用户身份、变量和回合彼此独立；后续修改来源数据不改变已有聊天。

### 3.1 定义的归属与字段

角色定义归属于角色，用户定义归属于用户身份。此处的用户仍指角色扮演中的用户身份，不是多用户账号。两类定义采用相同的条目结构；世界书式设定纳入这两类定义，不另列为第三类定义。

每条定义包含以下四个业务字段，归属关系见[数据模型](data-model.md)：

| 字段 | 含义 |
| --- | --- |
| 顺序 | 表达定义条目的排列顺序 |
| 是否启用 | 决定该条定义是否参与本次发送；未启用的条目不参与解析和请求包装 |
| 是否存在模板 | 标识内容是否需要模板解析；无模板时按普通文本提供 |
| 内容 | 定义的原始文本，可包含随变量变化的模板片段 |

定义向写作预设提供按序组织的已启用条目，其中内容为模板解析后的文本；无模板条目保留原文。

### 3.2 模板化与发送时解析

模板化允许一条定义中的部分文本根据当前最新变量变化。例如，当变量 `A > 10` 时使用一段描述，当 `A <= 10` 时使用另一段描述。此处仅说明条件行为，不规定模板语言或语法。

用户点击发送后，定义在即将交给写作预设包装请求时完成解析：

1. 收集当前角色和用户身份下已启用的定义，并按顺序组织。
2. 对标记为存在模板的定义，使用解析时的最新状态作为变量来源解析内容；无模板的定义直接使用原文。
3. 全部解析成功后，将得到的定义文本作为结构化写作材料交给写作预设。
4. 任意参与解析的定义出错，直接判定本次发送失败，不进入请求包装和模型调用；用户需要修改定义文本后重新发送。

解析结果仅用于本次请求，不覆盖定义原文。归档前重新生成回复时，同样执行该步骤。

定义模板解析与写作预设的请求包装是两个独立阶段：前者决定定义文本的本次内容，后者决定这些文本如何进入目标接口请求体。定义使用 Jinja2，写作预设使用 JavaScript，由 QuickJS 执行。

每次解析都使用当前聊天的最新状态。应用提供完整状态副本，由模板按需引用字段；首回合使用角色状态配置生成的初始状态。

### 3.3 状态的 JSON 表达与存储

状态变量以 JSON 形式表达和存储，支持嵌套组织世界信息、人物信息及其下属属性。顶级 `世界` 对象及其日期、星期、时间、地点四个字符串字段为必需项，允许其他字段。日期严格采用真实有效的 `YYYY-MM-DD`，星期只能为星期一至星期六或星期日，时间为 24 小时制 `HH:mm`，地点允许为空。日期和时间不接受首尾空白或格式猜测，星期不与日期联动校验。示例：

```json
{
  "世界": {
    "日期": "2024-11-14",
    "星期": "星期四",
    "时间": "17:53",
    "地点": "温州第二高级中学/校门外/学院东路街角"
  },
  "江清月": {
    "年龄": 16,
    "服装": {
      "外套": "深藏青校服外套(拉上大半)",
      "上衣": "白色校服衬衫",
      "鞋子": "黑色圆头小牛皮乐福鞋"
    },
    "姿势": "坐在车后座，下巴搁在窗沿望着他"
  }
}
```

模板可引用嵌套字段，例如“世界 → 时间”或“江清月 → 年龄”；Jinja2 模板通过 `state` 的方括号索引访问字段。应保留 JSON 值的类型，例如示例中的年龄是数字，日期和时间是字符串。

状态的初始值、结构、校验与修正规则、参考信息和更新规则均归属角色，并随角色复制到聊天中。Schema 定义状态结构、默认值及校验与修正规则。初始状态由其默认值生成；状态以增量指令更新，并保存完整快照，详见第 6.1 节。正常生成及聊天面板手动编辑的状态通过 JSON、Schema 校验修正及统一世界字段检查后保存。创建角色和修改 Schema 时也须验证其默认初始状态。数据修改入口按原文保存历史状态，检查 JSON、统一世界字段和记录关联，不执行 Schema。已有状态不自动迁移，可继续读取；再次保存时执行新约束。

## 4. 回合生命周期

### 4.1 生成与确认

1. 用户选择或新建聊天，选择写作预设并配置所需模型设置。
2. 用户点击发送，当前输入作为用户楼层显示。
3. 应用收集写作材料，根据最新变量解析已启用的定义；全部成功后，交给预设包装请求。
4. 调用部分执行一次模型请求，预设校验和拆解返回内容。
5. 成功时展示 AI 回复，等待用户确认；失败时不产生新的有效 AI 回复楼层。
6. 用户可以重新生成，或编辑用户楼层后重新生成。
7. 用户满意后点击归档，当前回合正文才正式落盘。

生成失败包括定义模板解析失败、调用失败、预设处理失败、返回格式不合要求等。定义模板解析失败时尚未调用模型，需要修改定义文本后重新发送。通过格式校验仅代表生成成功，不代表用户已经认可，也不代表回合已经正式保存。

### 4.2 归档

点击归档后的顺序：

1. 保存已确认的回合正文。
2. 更新并保存当前回合状态。
3. 使用更新后的状态生成并保存回合摘要。
4. 执行情节判定。
5. 如需生成情节，对指定范围生成并保存情节摘要。
6. 正文、状态、摘要和必要的情节均保存成功后，标记归档成功。

正文已落盘与归档成功是不同节点。初次归档缺少任意必要结果时，不允许发送下一回合。

第一版情节判定由状态日期和回合数直接计算，不调用模型、不设置兜底。情节摘要由模型生成，仍可能失败。

### 4.3 失败与重试

归档按顺序推进，发生错误时停在当前步骤。重试从当前未完成步骤继续，也支持没有留下错误记录的进程中断恢复。此前已保存的正文和结果保留，不重复创建回合，也不重新执行已成功的步骤。

情节摘要失败时，保留本次判定的范围供重试使用。归档成功后不再提供重新生成或整体重新归档。

### 4.4 归档后编辑

归档成功后，只允许手动编辑最新回合的摘要、状态和本次产生的情节。修改保存后立即生效，不自动重算其他结果。开始下一回合后，上一回合不再是聊天面板的编辑对象。

数据修改入口独立提供全量读取与批量增删改，可修改历史正文、状态、摘要、情节和归档字段。关联修改在同一事务内保存，提交前检查最终数据一致性；失败整批回滚。提交时检查读取版本，避免旧页面覆盖已有修改。修改后不自动执行模型、Schema、模板、预设或其他结果重算。

## 5. 分层记忆与写作上下文

### 5.1 三种剧情表示

写作请求中的剧情按时间顺序包含：

1. 历史情节：较早回合的浓缩摘要。
2. 回合摘要：中期回合逐回合的概要。
3. 最近回合：最新若干回合的完整用户输入与 AI 输出。

在应用装配的剧情材料中，同一回合只采用一种表示，避免在情节、摘要和正文之间重复覆盖。预设随后负责这些材料在接口请求中的具体表达。

### 5.2 装配规则

设 `T` 为已归档回合总数，`X` 为最近完整回合数，`Y` 为最小回合摘要数。当前待发送输入不计入 `T`。

- `T <= X`：只有最近完整回合。
- `X < T <= X + Y`：最近 `X` 个回合使用正文，其余使用回合摘要。
- `T > X + Y`：先将最近 `X` 个回合之外的部分表示为摘要，再从旧到新尝试用已有情节折叠。
- 不存在情节时，最近回合之前的所有内容继续使用回合摘要。
- 若使用下一个情节会导致剩余回合摘要少于 `Y`，停止折叠；不拆分该情节，也不跳过它去使用更晚的情节。
- 情节不能覆盖本次必须保留为完整正文的最近回合。

`Y` 是折叠约束，历史不足时不要求凑足 `Y` 个摘要。

例：`T = 20`、`X = 5`、`Y = 6`，已有情节 A（1—4）、B（5—8）、C（9—12）。本次使用：

| 表示 | 覆盖回合 |
| --- | --- |
| 情节 A、B | 1—8 |
| 回合摘要 | 9—15，共 7 个 |
| 完整正文 | 16—20，共 5 个 |

使用情节 C 会使摘要仅剩 3 个，因此暂不使用 C。

情节已经生成，不代表立即进入写作请求。被情节覆盖的原回合与回合摘要仍需保留。

### 5.3 提供给写作预设的材料

请求包装直接使用应用从数据库读取并完成必要解析的原文，按以下材料组织：

- 已启用且完成模板解析的角色定义与用户定义；无模板条目使用原文。
- First Message。
- 按上述规则选出的历史情节与回合摘要。
- 最近完整回合。
- 当前用户输入。
- 最新状态（JSON 结构）。

First Message 始终由应用提供，是否包含在实际请求中由预设决定。当前期望的预设逻辑是：当请求历史开始采用回合摘要时，First Message 消失；后续折叠为情节时不重新出现。

这个判断依据本次使用的历史表示，而不是数据库中是否已经保存摘要。

## 6. 四个内置归档模块

状态更新、回合摘要、情节判定、情节摘要均由模块内代码实现，不使用写作预设机制。归档模块读取 AI 输出时，只使用 `<content>` 内的正文；用户输入仍作为本回合内容提供。

### 6.1 状态更新

状态模型负责把过去状态推进到本回合对话结束后的世界状态，逐项检查变量，按本轮行动、对话和更新规则结算时间流逝、地点转移及其他变化。用户不必报时或逐项指定新值。尚未执行的计划不提前结算，过去摘要仅作为背景。该步骤仍在正文确认后运行，更新结果供下一回合使用。

状态更新流程：

1. 读取当前聊天的最新状态，首回合使用 Schema 默认值生成的初始状态。
2. 将旧状态、本回合用户输入与 AI 正文、最近若干回合摘要、角色参考信息、变量更新规则及用户身份名称提供给模型。旧状态在提示词中以 YAML 展示；最近摘要仅帮助理解情境，更新依据是本回合对话。
3. 模型输出 `<UpdateVariable>`，其中 `<Analysis>` 为简短结算结论，`<JSONPatch>` 为修改指令数组，支持 `replace`、`add`、`remove`。程序只应用修改指令，不保存结算说明。
4. 在旧状态副本上应用指令，再执行 Schema 校验和修正规则。
5. 保存本回合的完整 JSON 状态快照。

无效指令或执行失败的单条修改被跳过，其他修改继续。即使全部修改被跳过，只要最终状态通过校验，也可成功保存未变化的快照。模型调用、整体解析或最终校验异常时，本步骤失败，不保存新快照。

### 6.2 回合摘要

状态更新成功后生成回合摘要。输入包括本回合用户输入、AI 正文、更新后的状态及所需上下文。模型概括本回合的关键事件、人物互动和重要事实，并结合状态中的日期、时间和地点记录场景。输出以年月日、时分、地点为首行，随后用约150字以第三人称记录具体事实，不添加解读、评价或推演。保存非空原文后进入情节判定。

### 6.3 情节判定

模块支持多种判定方法，通过代码切换；第一版只实现跨日与回合数阈值判定。各方法共同遵守以下范围和输出约定：

- 已归纳回合不再进入情节判定候选；生成情节时仅允许最近一个旧情节的末回合作为只读桥接上下文，不重复归纳或改变覆盖范围。
- 候选范围为尚未归纳的回合，按时间排序。
- 不需要归纳时返回“否”。
- 需要归纳时返回截止回合，起始回合固定为最早尚未归纳的回合。
- 截止回合必须属于本次候选范围，归纳范围连续且包含两端。

例如候选为 13—20，返回 17，则归纳 13—17，留下 18—20。

第一版规则：

1. 取所有尚未归纳的回合，暂时排除最新回合。
2. 剩余回合不足 5 个时，返回“否”。
3. 要求最新回合与上一候选回合状态中的 `世界.日期` 都是严格 `YYYY-MM-DD` 格式的有效日期字符串，解析为日期值后比较，相同时返回“否”；达到门槛后日期缺失或类型无效则判定失败。
4. 日期不同时，返回上一回合为截止回合，将最新回合之前的全部候选归纳为情节；最新回合留待后续处理。

判定只读取回合范围及状态变量，不分析剧情文本，也不需要模型或兜底逻辑。

### 6.4 情节摘要与处理边界

情节摘要模块处理判定选定的范围。按序提供回合摘要、用户输入、AI正文及对应状态；首个情节包含First Message，后续可提供上一情节末回合的桥接信息。输出JSON包含不超过20字的标题和摘要，摘要以日期范围及地点开头，用约200~300字的一段话记录事件；标题和摘要分别保存。只有生成并保存成功后，这些回合才标记为已归纳，处理边界向前移动；失败时边界保持不变。

情节生成的边界与写作上下文装配独立。某个情节即使尚未被写作请求采用，其覆盖回合也不再进入后续情节判定。

## 7. 写作预设

### 7.1 职责与权限

预设只用于写作，第一版只支持一次模型调用的前后转换。

- 不执行模型调用。
- 不直接读写数据库。
- 不控制归档流程。
- 不决定前端展示方式。
- 可以包装完整的目标接口请求体，并解析该接口的返回内容。

### 7.2 请求包装

包装过程是一种带变量与处理逻辑的模板转换：

预设直接使用经过解析的数据库原文包装请求。进入该阶段的定义已完成模板解析，历史情节、回合摘要和最近回合按第 5 节选取；当前用户输入另行提供。

| 能力 | 示例 |
| --- | --- |
| 固定内容 | 提示词、固定消息、工具声明、接口参数 |
| 变量填充 | 定义、历史、状态、用户输入 |
| 条件与遍历 | 条件包含 First Message，遍历最近回合 |
| 内容变换 | 合并消息、调整角色、筛选已保存 AI 输出的标签区段 |

逻辑上提供的用户输入与 AI 输出，不强制对应最终接口中的同名角色。预设可以将最新输入与其他内容合并，也可以使用目标接口特有的角色和结构。

预设向调用部分返回 `{api_type, body}`，分别标识目标接口类型和完整请求体。

### 7.3 与模型设置的关系

预设目标接口与模型设置独立。两者不兼容时，由调用部分报错，不隐式将预设转换成另一种接口规范。

请求参数以预设显式提供的值优先，模型设置补充默认值。调用部分负责连接、鉴权、模型调用和调用错误；连接字段与递归默认参数合并规则见[模型调用](../backend/06-model-calls.md)。

### 7.4 回复解析与校验

接收转换的目标是确定哪些内容可以成为数据库中的“AI 输出”。

例如，预设要求模型只通过 `xxx` 工具的 `content` 参数输出，参数文本必须包含：

```xml
<think>...</think>
<content>...</content>
<other>...</other>
```

接收过程：

1. 从模型返回中提取指定工具调用的 `content` 参数。
2. 校验预设要求的标签是否存在且正确闭合。
3. 成功时返回可接受的 AI 输出文本。
4. 提取失败或校验失败时报告生成失败。

`<content>` 是供归档模块读取的 AI 正文区段；其他标签由预设决定。`think` 为自定义文本内容，不是原生思维链。

此类工具调用用于承载输出；提取参数不意味着要实际执行函数或追加第二次模型调用。

### 7.5 保存、再发送与展示

通过校验的 AI 输出保留预设认可的标签内容，等待用户点击归档后保存。

- 再次作为最近回合发送时，由请求包装决定是否包含 `think` 或其他区段。
- 归档时，各模块只读取 `<content>` 内的 AI 正文。
- 展示时，由前端解析设置决定如何呈现这些区段。
- 请求过滤与展示隐藏不改写数据库中的 AI 输出。

目前不需要为展示和上下文分别维护两份正文。完整模型响应是否另行保留为诊断记录，尚未确定。

## 8. 模块边界概览

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| 聊天与归档流程 | 回合生命周期、任务顺序、可用操作、保存结果 | 预设内部的内容包装细节 |
| 记忆装配 | 根据 X、Y 和情节范围选择历史表示 | 情节触发判定、接口消息格式 |
| 定义模板解析 | 根据解析时的最新状态解析已启用的定义，提供完整状态供模板按需引用，解析失败时中止发送 | 请求体包装、模型调用、覆盖定义原文 |
| 写作预设 | 请求包装、返回提取与校验 | 模型调用、数据库操作、前端渲染 |
| 调用部分 | 参数衔接、接口兼容检查、连接与模型请求 | 故事归档决策 |
| 四个归档模块 | 各自的摘要、状态或判定逻辑 | 可编程预设机制 |
| 前端解析 | 内容显示与渲染 | 修改用于保存的 AI 输出 |
